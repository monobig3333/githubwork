# 2-2 アラーム処理性能（最大負荷 30,000件/10分） 試験結果

## 判定: **OK**

## 試験方式

Zabbix サーバ上で `zabbix_sender` を一括実行し（`zabbixtool/send_bulk.py`）、
Zabbix トリガー → MID Server → ServiceNow `em_event` の経路で処理されることを確認する。

```
Zabbix サーバ (send_bulk.py) --localhost:10051--> trapper item
    → Trigger (OK→PROBLEM) → ServiceNow コネクタ → em_event
```

Mac 側は `2-2/watch_em_event.py` で到達件数を定期モニタし、
`2-2/count_zabbix_events.py` で Zabbix 側の生成数を突合する。

## 結果（2026/8/21・コネクタ ポーリング間隔 15 秒）

| 段階 | 実測 | 合否判定基準 | 判定 |
|---|---|---|---|
| Zabbix への投入 | **30,000 件 / 600.0 秒 / 50.0 件/秒 / 失敗 0** | 30,000 件 / 10 分 | ✅ |
| Zabbix でのイベント生成 | 約 30,000 件（50 件/秒） | — | — |
| **ServiceNow 到達** | **30,000 件** | — | — |
| **欠損** | **0 件** | 処理漏れ・スキップなし | ✅ |
| 取り込み完了まで | 36 分 30 秒 | — | — |

## コネクタ ポーリング間隔の比較検証

| | 30 秒条件（8/20） | 15 秒条件（8/21） |
|---|---|---|
| 到達件数 | 30,000（欠損 0） | 30,000（欠損 0） |
| 取り込み完了 | 約 37 分 | 36 分 30 秒 |
| 平均レート | 13.2 件/秒 | 13.3 件/秒 |
| 主バッチ間隔 | 約 215 秒 | 約 215〜233 秒 |
| 1 バッチの主サイズ | 3,000 件 | 3,000 件 |

**ポーリング間隔は律速ではない。** 1 サイクル約 215 秒のうち待ちは 30 秒のみで、
残り約 185 秒は 3,000 件の処理時間。間隔を半分にしても総時間は 30 秒程度しか縮まらない。
律速は「**1 サイクルあたり約 3,000 件**」という取得・処理の単位である。

## 判定理由

- 投入側は要件レート（50 件/秒 × 600 秒 = 30,000 件）を完全に達成し、失敗ゼロ
- **ServiceNow 側で 30,000 件すべてが登録され、処理漏れ・スキップはゼロ**
- 取り込み完了までは 37 分を要するが、前回（2026/6/2・nonprod）も 1,701 秒（28 分）で OK 判定と
  されており、「10 分間に 30,000 件という負荷を取りこぼしなく処理できること」という解釈を踏襲する
- 瞬間的には 3,000 件/分（= 50 件/秒）で登録されており、ServiceNow の受信能力自体は要件を満たす

## MID Server のメモリ設定が処理能力を左右する（重要な発見）

2026/8/19 の初回計測では、**30,000 件の投入に対し 13,500 件（54.8% 欠損）で処理が停止**した。
当時の dev MID は t3.small（2 GiB）で、**Java ヒープが 1024 MB** に設定されていた。

t3.large（7 GiB）へ拡張しても `wrapper.java.maxmemory` は自動では変わらず 1024 MB のままだった。
これを **4096 MB に変更しただけで、30,000 件すべてが到達し欠損がゼロになった。**

| 条件 | MID | Java ヒープ | 到達 |
|---|---|---|---|
| 2026/8/19 | t3.small (2 GiB) | 1024 MB | 13,500 / 30,000（**54.8% 欠損**） |
| 2026/8/20-21 | t3.large (7 GiB) | **4096 MB** | **30,000 / 30,000（欠損 0）** |

欠損は製品の処理能力ではなく **MID のメモリ設定**に起因していた。
設定は `conf/wrapper-override.conf` に記述する（`wrapper.conf` は MID アップグレードで上書きされる）。

## 投入ツールについて

従来の `zabbixtool/on.py` は 1 イベントごとに `zabbix_sender` プロセスを起動するため、
`sleep(0.02)` を入れても **実効 12.5 件/秒**しか出ず、30,000 件に約 40 分かかっていた。
要件の 50 件/秒を満たせないため、`zabbix_sender -i -` で 1 秒ごとに 50 件を一括送信する
`zabbixtool/send_bulk.py` を新規作成し、**30,000 件 / 600 秒 / 50.0 件/秒 / 失敗 0** を達成した。

前回（2026/6/2・nonprod）に記録された「実効 17.6 rps・880 件失敗」も、投入方式に起因していた
可能性が高い。

## 試験手順上の注意

Zabbix は **OK → PROBLEM の遷移でしかイベントを生成しない**。連続して試験を行う場合、
毎回、事前に全トリガーを復旧させる必要がある。

```bash
python3 send_bulk.py --count 30000 --rate 50 --value 0   # ① 復旧（10 分）
# ② PROBLEM が 0 件になったことを確認
# ③ 復旧イベントが ServiceNow に流れ切るまで待つ（30〜40 分）
python3 send_bulk.py --count 30000 --rate 50             # ④ 投入
```

③を省くと復旧イベントが今回分に混ざり、到達数が読めなくなる。
